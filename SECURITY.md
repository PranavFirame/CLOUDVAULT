# CloudVault: Security Architecture & Threat Model

## 1. Zero-Knowledge Security Model

CloudVault enforces client-side zero-knowledge encryption:
* **Browser Trust Boundary:** The browser runtime is responsible for master key generation, passphrase key derivation, file-encryption key generation, file data encryption/decryption, and metadata encryption/decryption.
* **Server Trust Boundary:** The backend server and local database manage authenticated sessions, store encrypted ciphertext envelopes, and validate access boundaries. The backend never receives the vault passphrase, the plaintext master key, individual file keys, or unencrypted file contents.

---

## 2. Cryptographic Hierarchy

```
[Vault Passphrase] 
       │ (Argon2id: 64MB memory, 3 iterations, 4 parallelism, 16-byte random salt)
       ▼
 [Key-Encryption Key (KEK)] 
       │ (AES-256-GCM, 96-bit nonce, AAD: "CloudVault-MasterKey-v1")
       ▼
[Master Key (256-bit CSPRNG)] ───► Transient Browser Memory Only
       │
       ├─► HKDF-SHA256 (Info: "CloudVault-FEK-Wrap-v1:" + fileId)
       │         │
       │         ▼
       │   [Wrapping Key] (AES-256-GCM) ───► Wraps Per-File Key (FEK)
       │
       └─► AES-256-GCM ───► Encrypts File Metadata (Name, Size, MIME)
```

### Cryptographic Invariants
1. **Payload Cipher:** AES-256-GCM with 128-bit authentication tags.
2. **KDF:** Argon2id with 65,536 KB memory cost, 3 iterations, 4 parallelism lanes, and 16-byte unique cryptographic salt.
3. **Nonce Freshness:** Every AES-GCM operation uses a unique 96-bit (12-byte) nonce generated by `crypto.getRandomValues()`. Nonce reuse is strictly prohibited.
4. **Additional Authenticated Data (AAD):** Ciphertext is bound to the immutable `fileId` and version identifier (`CloudVault-FileContent-v1:${fileId}`). Attempting to substitute or re-assign ciphertext to a different file ID causes decryption to fail.
5. **Memory Key Scrubbing:** Upon locking the vault or logging out, master key buffers in browser memory are overwritten with zeroes (`masterKey.fill(0)`). Note that due to JavaScript engine garbage collection optimizations, memory clearing is best-effort and cannot guarantee that transient copies in internal V8 heap pages are wiped instantly.

---

## 3. Separate Account Password vs. Vault Passphrase

* **Account Password:** Used exclusively for server-side session authentication. It is salted with 16 bytes of entropy and hashed on the server using `scrypt` (N=16384, r=8, p=1). The account password cannot unlock the encrypted vault.
* **Vault Passphrase:** Used exclusively in the browser to derive the KEK and unlock the Master Key. It is never transmitted across any network or HTTP API, and is never persisted in cookies, `localStorage`, `sessionStorage`, PostgreSQL, or Redis.

---

## 4. Disaster Recovery & Passphrase Rotation

* During vault setup, an independent 128-bit entropy recovery secret is generated (`CV-XXXX-XXXX-...`).
* A recovery copy of the master key is wrapped under the recovery key (`CloudVault-RecoveryKey-v1`).
* If a user forgets their vault passphrase, they can decrypt the master key envelope using the recovery secret, choose a new passphrase, and re-encrypt the master key without losing access to any previously uploaded files.
* **Irreversible Loss Warning:** If a user loses both their vault passphrase and recovery secret, data is cryptographically unrecoverable. No administrative backdoors exist.

---

## 5. Threat Mitigations & Limitations

### Mitigated Threats
* **Server Compromise / Database Leak:** A stolen PostgreSQL dump or intercepted disk contains only ciphertext and encrypted envelopes. Files cannot be decrypted without client passphrases.
* **Ciphertext & Metadata Tampering:** Any modification of ciphertext or metadata triggers an AES-GCM authentication tag mismatch and terminates decryption immediately.
* **Path Traversal & Symlink Attacks:** Storage identifiers are strictly validated against `^[a-zA-Z0-9_-]{16,64}$` and resolved exclusively within the designated `./data/objects/` root directory.
* **Brute-Force & Denial of Service:** Redis sliding-window rate limiting protects registration, login, and upload endpoints. If Redis fails, fail-safe in-memory rate limiting continues enforcement.

### System Limitations & Unmitigated Threats
* **Host Machine Compromise:** If an attacker possesses root/administrator privileges on the physical computer hosting CloudVault, or installs a malicious browser extension / keylogger, they can inspect process memory, read keystrokes, or tamper with frontend code bundles.
* **Browser Security Sandbox:** Security relies on modern browser implementations of the Web Crypto API (`SubtleCrypto`).
